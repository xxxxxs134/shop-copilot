# 场景案例库：店智 Copilot 的 12 段对话

> 店智 Copilot 是面向客户的电商智能客服 Agent。本文件覆盖售前（商品咨询、推荐、库存）与售后（查订单、退款/退货受阻诊断、改地址、拦截物流、政策问答、投诉升级）两类场景，以及意图澄清与幻觉防御。
> 每个场景标注意图分类（Router 四类：presales / aftersales / escalation / clarify）、路由走向、推理链与技术点，可直接当演示脚本或验收用例跑。
> 订单号、商品、售后单均来自本地种子库（`python -m backend.app.agent.seed_store`），金额与状态可复现。

---

## 场景 1：售前·商品咨询与推荐

**用户输入**："你们有什么适合送父母的礼物吗？"（能力卡「售前推荐」原题）
**意图分类**：presales（售前咨询）
**路由**：Router → 售前客服 → 终审（意图 chip：售前咨询 · → Agent 工具）
**Agent 推理链**：
1. 💭 送礼场景，预算没说，先把在售商品扫一遍，按"适合长辈"挑几款，每款给一句理由。
2. 🔍 product_lookup(keyword="") → 12 个 SKU 中筛出：加厚珊瑚绒毯 129 元（库存 75）、不锈钢保温饭盒 89 元（库存 130）、LED 化妆镜带灯 119 元（库存 88）；老款帆布双肩包已下架不推。
3. 💡 按实用度推 3 款，追问预算收窄范围。

**输出**：
> 送父母推荐这几款：
> 🧣 加厚珊瑚绒毯 129 元——秋冬保暖实用，家里都用得上；
> 🍱 不锈钢保温饭盒 89 元——带饭方便，爸妈出门也能吃口热的；
> 💄 LED 化妆镜带灯 119 元——梳妆看得清，妈妈用着顺手。
> 都是现货。您预算大概多少？我再帮您缩小范围。

**技术点**：Router 四类意图分流（presales）+ 售前工具集隔离（仅 product_lookup / kb_search）+ product_lookup 空关键词全量扫描 + 终审统一语气 + 追问预算不编造

## 场景 2：售前·库存查询

**用户输入**："儿童保温杯还有货吗？"
**意图分类**：presales（售前咨询）
**路由**：Router → 售前客服 → 终审
**Agent 推理链**：
1. 💭 点名查库存，直接查这个 SKU，不用绕。
2. 🔍 product_lookup(keyword="儿童保温杯") → 69 元，库存 2，状态在售（低库存）。
3. 💡 如实报数 + 低库存提醒，不夸大。

**输出**：
> 儿童保温杯还有货：69 元，当前库存仅剩 2 件，在售中。
> 库存不多了，喜欢的话建议尽快下单；要我帮您看看同价位的其他杯子吗？

**技术点**：product_lookup 模糊匹配 + 低库存自动提示 + 终审只保留工具证据（不编"还有很多货"）

## 场景 3：意图不明·追问澄清

**用户输入**："那个东西怎么样？"
**意图分类**：clarify（待澄清）
**路由**：Router → 追问澄清 → END（不进专业 Agent，不浪费工具调用）
**Agent 推理链**：
1. 💭 "那个东西"没有指向任何商品或订单，进哪个专业 Agent 都会瞎猜。
2. 🔍 （无工具）Router 置信度低 → clarify 节点生成一句追问。
3. 💡 直接反问，单步结束。

**输出**：
> 您好！请问您是想咨询或选购商品，还是查询已有订单或售后问题呢？

**技术点**：Router 四类意图之一 clarify + clarify 节点单步 END + thought_chain 留痕（router → clarify）+ 无工具时终审放行追问式（草稿含？/请提供等标记）

## 场景 4：售后·查订单物流（两轮）

**用户输入（第一轮）**："我的订单到哪了？"（能力卡「查订单」原题）
**用户输入（第二轮）**："SO20261027009"
**意图分类**：aftersales（售后处理）
**路由**：Router → 售后客服 → 终审
**Agent 推理链**：
1. 💭（第一轮）没给订单号，售后规矩是先追问，不能瞎猜单。
2. 🔍（第一轮，无工具）追问订单号 → 终审按"追问式"放行。
3. 💭（第二轮）拿到单号，查状态和物流；客户在催，附一句能直接回的话术。
4. 🔍（第二轮）order_lookup(order_id="SO20261027009") → 郑*，不锈钢保温饭盒 ×2，实付 178 元，shipped，10-21 发货，圆通速递 YT9182736455102。
5. 💡 订单卡片 + 物流进度 + 安抚话术。

**输出**：
> （第一轮）请告诉我您的订单号，我帮您查～
> （第二轮）订单 SO20261027009 · 不锈钢保温饭盒 ×2 · 实付 178 元
> 状态：已发货，圆通速递 YT9182736455102（10-21 发货）
> 话术可直接复制："亲，您的饭盒已经发出啦，物流单号 YT9182736455102，有更新我随时同步您～"

**技术点**：AFTERSALES_SYSTEM「无单先问」+ review 硬校验放行追问式 + order_lookup 订单与售后单合并返回 + 工具结果 600 字证据截断 / 4000 字 token 预算防上下文爆 + SqliteSaver 跨轮记忆（thread_id = 会话 ID）

## 场景 5：售后·退款被拒诊断（平台自助）

**用户输入**："SO20261027011 的退款被拒了，为什么？我该怎么办？"
**意图分类**：aftersales（售后处理）
**路由**：Router → 售后客服 → 终审
**Agent 推理链**：
1. 💭 退款不再由客服 Agent 执行；先查订单与售后单，确认申请状态，再查政策解释原因。
2. 🔍 order_lookup(order_id="SO20261027011") → 订单已收货，商品 LED化妆镜带灯 ×1，实付 119；售后单状态「被拒」。
3. 🔍 kb_search("退款 被拒 申诉 售后政策") → 命中退款处理流程、售后争议与平台申诉相关切片，取前 2–3 条。
4. 💡 说明可能原因（超出售后期/证据不足/商品状态不符等），列出需要补充的证据，给三条路径：回订单页重新申请、发起平台申诉、升级投诉/人工。
5. 💡 明确边界：不承诺「我帮你退款」或「已退款」；退款动作留在平台订单页。

**输出**：
> 这单的售后单状态是「被拒」，所以现在不是退款成功。常见原因有三类：超过售后期、证据不足、商品状态不符合退款条件。你可以先回订单页看拒绝原因，补齐商品问题照片/物流凭证后重新申请；如果商家仍不处理，可以在平台发起申诉或升级投诉。需要的话，我可以按政策帮你把申诉要点整理成一段话。

**技术点**：退款只读诊断（不执行）+ 订单/售后状态查询 + RAG 政策引用 + 不越权承诺

## 场景 6：售后·退款被拒（金额超限）

**用户输入**："SO20261027001 退 418 吧，我看到别家同款才卖这个价"
**意图分类**：aftersales（售后处理）
**路由**：Router → 售后客服 → 终审
**Agent 推理链**：
1. 💭 418 比实付 159.8 还高，八成过不了。别替规则说话，先让后端打回来，再给合规的路子。
2. 🔍 refund_flow(action="validate", order_id="SO20261027001", amount=418) → ok=false，violations=["退款金额 418 超过实付金额 159.8"]，未签发令牌。
3. 💡 转述拒因，说清只能按实付退，另外给两条不违规的替代方案。

**输出**：
> 这单退不了 418。后端校验打回：退款金额 418 超过实付金额 159.8。
> 合规做法有两个：一是按实付 159.8 元整单退；二是走价保流程补差价（补的是差价不是退款）。要走哪个我接着办。

**技术点**：validate 拒绝分支 + violations 列表原样转述 + 业务校验在后端（模型说了不算）+ 拒绝不中断对话（作为 tool result 回给模型继续答）

## 场景 7：售后·修改收货地址（两段式）

**用户输入（第一轮）**："SO20261027002 地址改一下，改成江苏省南京市鼓楼区中山北路 105 号"
**用户输入（第二轮）**："确认修改"
**意图分类**：aftersales（售后处理）
**路由**：Router → 售后客服 → 终审
**Agent 推理链**：
1. 💭 改地址也是敏感操作，走同一套两段式：校验 → 客户确认 → 执行。订单是 paid 未发货，能改。
2. 🔍 modify_address(action="validate", order_id="SO20261027002", new_address="江苏省南京市鼓楼区中山北路 105 号") → 订单存在 ✓ 未发货 ✓ 新地址非空 ✓ → {ok:true, preview, token}。
3. 💡（第一轮）复述新旧地址问"确认修改吗？"
4. 🔍（第二轮）modify_address(action="execute", token="…") → 凭令牌执行 → 回执（幂等：重复执行只回"已修改地址"）。

**输出**：
> **预览**：SO20261027002（便携式充电宝 ×1 · paid）收货地址将改为：江苏省南京市鼓楼区中山北路 105 号。确认修改吗？
> **回执**：✓ 收货地址已修改。

**技术点**：modify_address 两段式门控（与 intercept_logistics / return_exchange 同一套令牌机制）+ 后端状态校验（已发货订单会打回"订单已发货，无法修改收货地址"）+ 令牌锁定地址参数（execute 忽略模型再传的值）

## 场景 8：售后·拦截物流（两段式）

**用户输入（第一轮）**："SO20261027007 别发货了，我不要了"
**用户输入（第二轮）**："确认拦截"
**意图分类**：aftersales（售后处理）
**路由**：Router → 售后客服 → 终审
**Agent 推理链**：
1. 💭 订单已发货，改地址来不及，走拦截。先校验能不能拦。
2. 🔍 intercept_logistics(action="validate", order_id="SO20261027007") → shipped ✓ 有运单（顺丰 SF7392846152738）→ {ok:true, preview 含运单信息, token}。
3. 💡（第一轮）复述运单，问"确认拦截物流吗？"
4. 🔍（第二轮）intercept_logistics(action="execute", token="…") → 拦截提交回执（每单限一次；已签收会打回"包裹已签收，无法拦截物流"）。

**输出**：
> **预览**：SO20261027007 · 顺丰速运 SF7392846152738 · 包裹在途，可尝试拦截。确认拦截吗？
> **回执**：✓ 物流拦截已提交。若承运商已派送可能拦截失败，届时请拒收退回。

**技术点**：intercept_logistics 两段式 + 仅已发货订单可拦截（paid/received 状态后端拒绝）+ preview 携带运单供客户核对 + 每单限一次

## 场景 9：售后·退换货 + 情绪安抚（模糊描述）

**用户输入（第一轮）**："我收到的毯子有问题想退，急死了"（能力卡「退款退货」变体）
**用户输入（第二轮）**："SO20261027015"
**意图分类**：aftersales（售后处理）
**情绪**：焦虑（急死了）· 实体：商品=毯子、action=退货
**路由**：Router（带情绪）→ 售后客服 → 终审
**Agent 推理链**：
1. 💭 "急死了"是焦虑，先安抚再办事；没给订单号，按商品名+近期订单定位。
2. 🔍（第一轮，无工具）安抚 + 追问订单号；（第二轮）order_lookup 定位 SO20261027015（加厚珊瑚绒毯 ×2 · 258 元 · received · 10-23）→ return_exchange(action="validate", order_id="SO20261027015", return_type="退货退款", reason="商品有问题") → 已收货 ✓ 7 天内 ✓ 无进行中售后 ✓ → {ok:true, preview, token}。
3. 💡 复述预览问"确认办理退换货吗？"，停在确认前等回复。

**输出**：
> （第一轮）实在抱歉让您着急了！请告诉我订单号或商品名，我马上帮您查～
> （第二轮）定位到 SO20261027015（加厚珊瑚绒毯 ×2 · 实付 258.00 元 · 已收货）。
> **预览**：办理退货退款，退款金额 258.00 元原路退回，需先寄回商品。确认办理吗？

**技术点**：Router 同次调用产出情绪（chip 显示"焦虑"徽章）+ 实体线索引导追问 + return_exchange 两段式（validate → 确认 → execute 生成"待寄回"单据）+ 已发货未收货订单会被打回（"请先确认收货或拦截物流"）

## 场景 10：售后·政策问答（知识库引用）

**用户输入**："退货政策是什么？拆封了还能退吗？"
**意图分类**：aftersales（售后处理）
**路由**：Router → 售后客服 → 终审（回答带 [1][2] 角标）
**Agent 推理链**：
1. 💭 规则类问题走知识库，回答要能溯源，客户较真的时候好对质。
2. 🔍 kb_search("退货政策 拆封 无理由") → RRF 融合检索命中《客户申请退款的处理流程》（客服与售后）《发货超时的后果与应对》（物流与仓储）等切片，取前 2–3 条。
3. 💡 生成回答，句尾挂 [1][2]，鼠标点开来源卡片。

**输出**：
> 拆封能否退分情况：未发货的直接退即可；已发货的先确认货物状态——在途可引导拦截，已签收按"七天无理由"或质量问题流程处理；定制类、贴身类等特殊商品以上架时明确标注的规则为准 [1]。质量问题或描述不符的，快速退换加运费承担通常比争辩更划算 [2]。
> （点击 [1] 弹出来源卡片：《客户申请退款的处理流程》分类"客服与售后"，原文片段可见）

**技术点**：kb_search 混合检索（jieba BM25 + 向量 RRF）+ kb_hits 单独收集供终审注入 [n] 引用指令 + 有命中但答案缺 [n] 记警告日志 + CitationCard 溯源（标题 / 分类 / 原文片段）+ 流式 Markdown 渲染

## 场景 11：知识未覆盖·诚实拒答（幻觉防御）

**用户输入**："找个主播带货一般给多少坑位费？提点比例多少合适？"
**意图分类**：aftersales（售后处理）——问题偏市场行情，工具与知识库均不覆盖
**路由**：Router → 售后客服 → 终审（硬校验拦截）
**Agent 推理链**：
1. 💭 这个问题偏市场行情，商品库、订单库、知识库里都未必有。先检索，查不到就不编。
2. 🔍 kb_search("主播 坑位费 提点") → 最高分切片与坑位费行情不沾边或 found:false；order_lookup/product_lookup 也无此类字段 → 无有效证据。
3. ⚠️ 终审硬校验：无工具证据 + 无知识库命中 + 草稿非追问式 → 强制拒答（不放行凭模型知识编造的数字）。

**输出**：
> 抱歉，这个问题我暂时没有查到确切信息，建议您联系人工客服进一步确认。
> （若知识库有沾边内容会先给 [1] 指引，并说明行情类数据建议按品类对比几家 MCN；拿到靠谱区间后补进知识库 /kb，下次即可回答）

**技术点**：review_node 硬校验①（无证据且非追问 → 强制拒答，不靠 LLM 自觉）+ 诚实原则不瞎编数字 + 追问式与事实断言分流（草稿含？/请提供等标记才放行）+ /kb 补录闭环

## 场景 12：投诉升级（情绪愤怒 → 工单）

**用户输入**："你们也太慢了吧，催了三次了，气死了我要投诉！"（能力卡「投诉建议」升级版）
**意图分类**：escalation（投诉升级）
**情绪**：愤怒（气死了 / 催了三次）· 实体：action=投诉
**路由**：Router → 投诉升级专员 → 终审（告知工单号）
**Agent 推理链**：
1. 💭 "催了三次"是反复未果，"气死了"是愤怒，还带着投诉意图。这类问题工具闭环不了，直接升工单。
2. 🔍 escalation_node → chat_json(ESCALATION_PROMPT) → {ticket_id: "TK-2026…", issue_category: "物流催单", urgency: "high", suggested_action: "优先致歉+给出明确解决时限"}。
3. 💡 终审走工单分支：温和告知已受理 + 工单号；对话页头「投诉处理方案」可再调 /v1/escalate 拿摘要/建议/可复制话术（仅投诉会话显示）。

**输出**：
> 这边真的很抱歉，催了三次还没解决，是我们没做到位。您的问题已受理并转人工优先处理。
> **工单号**：TK-20261027143012 · 类别：物流催单 · 紧急度：high
> 可复制话术："非常抱歉让您久等了，我已经帮您加急，今天之内给您明确答复。"

**技术点**：Router escalation 分支（不进售前/售后工具集）+ chat_json 结构化工单（TK- 时间戳单号）+ 终审工单分支（告知受理+工单号）+ /v1/escalate 处理方案（情况摘要 / 建议动作 / 可复制话术）+ 情绪识别愤怒（chip 红标）
